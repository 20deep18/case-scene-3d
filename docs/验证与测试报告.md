### 4.4 「点击标注列表 → 三维区黑屏」（第四轮修复，NaN 污染）

用户反馈：**「在标注与物证板块单击选择一个项目时，中间的模型展示区会直接黑屏，
需要重新载入三维现场。」**

**复现证据**（`tests/repro_annot_blackout.mjs`，真实浏览器读回像素）：

```
相机（点前）: {"pos":[8.07,6.36,8.08]}          ← 正常
  载入模型后     非零像素 145432  drawn 121920   ← 正常出图
  点击 测距B     非零像素      0  drawn 121920   ← 黑屏，但 draw 调用仍在发生
相机（点后）: {"pos":[null,null,null]}          ← 相机位置变成 NaN
```

**根因链**（三层）：

1. `state.bounds` **从来没有被赋值** —— 载入模型时只写了 `state.picker.bounds`，
   而 `focusAnnotation` 读的是 `state.bounds`。
2. 于是 `state.bounds?.radius * 0.4` 里 `undefined * 0.4 = NaN`。
3. 关键陷阱：写成 `... ?? 1` 以为能兜住，但 **`??` 只处理 `null`/`undefined`，
   `NaN ?? 1` 仍然是 `NaN`**。
4. `dist = NaN` → `camera.position` 变成 NaN → 整个矩阵链 NaN。
   渲染器照样发出 12 万个 draw，但全部落在无效坐标上 —— **整屏黑**，
   而且无法自愈，只能重新载入模型。

**修复**：

| 改动 | 说明 |
| --- | --- |
| `loadModel` 里补上 `state.bounds = bounds` | 修掉根因；此后场景尺度几何（网格、飞行速度、定位距离）也都正确了 |
| 新增 `finiteOr(value, fallback)` 工具函数 | 把 6 处 `?.radius * k ?? 默认值` 全部换掉。`??` 兜不住 NaN，这类写法必须用「取到数值再判断有限性」 |
| `focusAnnotation` 入口校验 + 出口兜底 | 标注坐标无效或算出的位置非有限数时**宁可不移动相机**，并 console.warn + toast，绝不把 NaN 写进相机 |
| 定位距离夹到场景尺度区间 | 并让视线在标注远离场景中心时偏向中心，避免相机停在模型内部（也会黑屏） |

**回归断言**（已写进 `tests/browser_render_check.mjs`）：

```
  [OK]   场景尺度 state.bounds 已写入且为有限数  radius=5.2473360956297475
  [OK]   点击标注列表不会把相机位置变成 NaN（黑屏根因）  检查了 1 个条目
  [OK]   点击标注后三维区仍有内容  241005 像素
```

> 教训：**永远不要用 `??` 去兜住一个「可能产生 NaN 的算术表达式」**。
> 单元测试完全测不出这个问题（它只在真实交互路径上触发），
> 必须靠真实浏览器回归 + 「读回画布像素」这种硬指标。

## 六、真实浏览器交互缺陷修复记录（第二轮）

第一轮只做了「CPU 复刻着色器数学」的验证，没有真正在浏览器里跑起来。用户实际交互后
暴露了 4 个只在真实 WebGL2 环境才会出现的问题。已全部修复，并补上真实浏览器回归测试
（`tests/browser_render_check.mjs`，15 项断言）。这一节如实记录，因为它们非常典型。

### 6.1 「点击载入三维现场后显示顶点着色器编译失败」

**根因**：顶点着色器用了 `transpose(mat3)`。这是桌面 GLSL 的函数，
**GLSL ES 3.00（WebGL2）规范里没有 `transpose()`**，ANGLE 直接报
`'transpose' : no matching overloaded function found`。

原来的报错只显示「顶点着色器编译失败」，看不出是哪一行。现已改为把驱动原始日志
**连同带行号的源码**一起抛出并显示，同时新增 3 处避免同类问题的写法：

| 位置 | 问题写法 | 修正 |
| --- | --- | --- |
| `splat-renderer.js` 顶点着色器 | `transpose(M)` | 手工转置（写出 9 个分量） |
| `splat-renderer.js` 顶点着色器 | `const float C2[5] = float[5](...)` | 改为独立 `const` 标量（ANGLE 对函数内常量数组构造支持不稳） |
| 着色器注释 | 注释里出现反引号 | 会提前结束 JS 模板字符串 → 已改写 |

### 6.2 「三维现场已载入但画面全黑」（最隐蔽的一个）

这里有**两个独立缺陷叠加**，都会导致「绘制调用成功、GPU 在跑、但画面什么都没有」：

1. **顶点属性 location=0 被当成无效值**
   ```js
   // 错误：!0 === true，于是 position(location=0) 被整个跳过
   if (!attrName || attrName < 0) return null;
   ```
   `enableVertexAttribArray(0)` 从未执行，`position` 一直是 0 → 所有高斯都被判为
   相机背后（`camPos.w <= 0.0001`），片元被丢弃。修正为 `attrName == null || attrName < 0`。

2. **颜色属性重复归一化**
   ```js
   gl.vertexAttribPointer(loc.color, 4, gl.UNSIGNED_BYTE, true, 0, 0); // normalized = true
   ```
   着色器里是 `c.rgb / 255.0`。GPU 先归一化到 0..1，着色器再除 255，
   得到 0..1/255，于是 `vAlpha` 全部趋近 0，片元着色器的
   `if (alpha < 1.0 / 255.0) discard;` 把**每一个**像素都丢弃。修正为 `normalized = false`。

另外两处配套修复：

- **画布绘制缓冲一直是默认的 300×150**：`resize()` 依赖 `state.renderer`，而启动时的
  那次 `resize()` 发生在渲染器创建之前。现已在渲染器创建后立刻重算一次。
- **索引缓冲排序写错 VAO**：`ELEMENT_ARRAY_BUFFER` 的绑定属于 VAO 状态，
  `_sort()` 里必须先在 `bindVertexArray(chunk.vao)` 之后再 `bufferSubData`，
  否则排序结果写进了默认 VAO，该块仍用未排序的旧索引。

还在 `setData()` 里加了一道**装配自检**：VAO 装配完成后逐个检查顶点属性是否 enabled，
不满足就写 `console.error` 并记录到 `stats.attribError`。这类 bug 肉眼极难发现，
必须让代码自己喊出来。

### 6.3 「导入视频黑屏」+「只导入一个视频却出现两个相机对象」

**黑屏根因**：上传接口返回的 URL 少了 `media` 这一段。文件实际落在
`data/projects/<案件ID>/media/<文件名>`，而返回的是 `/media/<案件ID>/<文件名>`，
于是 `/media` 路由解析到不存在的路径，**所有视频与图片都 404**（浏览器表现为黑屏）。
现已返回 `/media/<案件ID>/media/<文件名>`；`repro_video_upload.mjs` 验证
`200 / video/mp4 / accept-ranges: bytes`、Range 请求返回 `206`、下载字节逐位一致。

同时修掉两处会加重黑屏的隐患：

- 同源视频原本也设置 `crossOrigin='anonymous'`，会多触发一次 CORS 校验；
  现只对真正的跨域资源设置，并注册 `error` 监听把失败原因打到控制台。
- 新相机默认建在原点（常常在墙体内部，看起来像没反应）。现改为按场景包围盒
  自动放到外侧、朝向场景中心，并在导入后立刻挂载画面、选中该相机。

**「两个对象」根因**：`POST /annotations` 带已有 id 时会**再插一条**而不是更新。
已改为幂等 upsert（命中已有 id 走更新，事件记为 `annotation.upsert`），
前端 `commitAnnotation` 也按 id 去重，对话框导入加了防重入标志。
`test_annotation_idempotent.mjs` 覆盖 9 项（重复提交、PATCH、media 不累积等）。

### 6.4 「帧率显示 60000FPS」

**根因**：`fpsAcc += 1000 / Math.max(dt, 1e-3)`，dt 下限只保护到 1ms，
一旦出现极小间隔就会算出上千的瞬时 FPS；而且累加器还是「平均值的平均」，越滚越怪。

现已重写：

- 改为**固定 500ms 时间窗计数** `frames * 1000 / windowMs`，稳定且直观。
- dt 下限改为 1/1000 秒、上限 0.1 秒，避免极小/极大间隔污染动画与统计。
- 新增 **60FPS 上限**：距上一帧不足 16.67ms 时先用 `setTimeout` 补足再
  `requestAnimationFrame`，不再空转。
- 页面切到后台时暂停渲染循环，回到前台重置计时（省电，也避免 dt 巨大）。

浏览器实测：软件渲染（SwiftShader）下稳定在 34 FPS，HUD 显示 34 FPS，不再出现异常值。

### 6.5 附带的交互改进

- 标注列表**双击原本直接删除**（想「双击定位」时极易误删）。现改为：
  双击 = 定位，删除需要点行尾出现的 `✕` 按钮并二次确认；属性面板的删除也加了确认。
- 新相机导入后会立即挂载画面并选中，属性面板新增「贴回现场并播放」按钮。

### 7.1 关于 8GB 显存的硬约束（重要）

自研 `train_gpu.py` 用纯 PyTorch 算子渲染，每个瓦片的中间张量规模随
「分辨率 × 瓦片内高斯数」增长。在本机 RTX 5060 Laptop（8151 MiB）上实测：

| 训练分辨率 | max-gaussians | 结果 |
| --- | --- | --- |
| 240×135（`--downscale 4`） | 45000 | ✅ **可完整跑完 1200 次迭代**（损失 0.178 → 0.0095） |
| 480×270（`--downscale 2`） | 45000 | ❌ 第 450 步左右 OOM（显存涨到 11.7GB） |
| 960×540（`--downscale 1`） | 40000 | ❌ 第 300 步左右 OOM |

因此**默认参数已设为 `--downscale 3 --max-gaussians 60000`**，
在 8GB 卡上请用 `--downscale 3~4`；12GB 以上可以试 `--downscale 2`。
低分辨率训练出的模型细节偏少（表现为画面偏暗、颗粒感强），这是本方案的已知代价。

> 想获得官方级别的训练质量，请在**有 MSVC + CUDA Toolkit 的机器**上编译 gsplat
> 或原版 3DGS，然后用 `pipeline/to_splat.py` 转换——两者导出的 PLY 格式完全兼容。
> 或者直接用手机 App（Polycam / Luma AI）导出的 `.ply` 走高保真替代路线（部署文档 §6.5）。

模型训练完成后仍可手工调优后处理，例如抽稀与去噪：

```powershell
# 按不透明度抽稀一半，减小文件
pyruntime312\python.exe pipeline\to_splat.py --ply ...\point_cloud.ply --out data\models\x.splat --decimate 0.5
# 剔除低不透明度噪点（阈值越小删得越多）
pyruntime312\python.exe pipeline\to_splat.py --ply ...\point_cloud.ply --out data\models\x.splat --min-opacity 0.05
```

## 九、第五轮：让「开始建模」真的能用（2026-10-05）

用户反馈：**「开始建模」功能不能正常工作，估计是视频/照片数量不够**；
并要求加一道「素材体积门槛」，门槛值必须**在实际训练中求得**。

排查结果：**不是「数量不够」，而是四个真实缺陷叠在一起**。下面是逐个根因与证据。

### 9.1 根因一：素材路径没有 URL 解码（用户看到的现象就是它）

上传接口把文件名编码进 URL：

```
/media/case-20261003/media/%E6%B5%8B%E8%AF%95%E8%A7%86%E9%A2%91.mp4
```

`app/server/index.js` 在收集建模素材时**直接把这串字符当磁盘路径**：

```js
const rel = String(a.url).replace(/^\/media\/[^/]+\//, '');
const abs = safeJoin(DATA_DIR, `projects/${projectId}/${rel}`);   // ← rel 里仍是 %E6%B5%8B…
```

于是流水线拿到的是**字面量 `%E6%B5%8B…` 这种不存在的文件**。任务日志（修复前的真实日志）：

```
[警告] 视频不存在，跳过：…\media\%E6%B5%8B%E8%AF%95%E8%A7%86%E9%A2%91%EF%BC%88%E8%BE%83%E5%A4%A7%E5%9E%8B%EF%BC%89.mp4
[信息] 可用于重建的图片总数：0
[错误] 可用于重建的图片太少（< 8 张）。请上传更长的视频或更多图片。
[系统] 任务失败：流水线退出码 2：参数或数据错误（素材不足、目录缺失）
```

**用户看到的是「素材不足」并因此以为是数量问题，真相是路径没解码** —— 那句「素材太少」
把排查引向了完全错误的方向。

修复：`mediaFileNameFromUrl()` 统一 `decodeURIComponent`；`pipeline/recon_job.py`
再加一层「解码后重试」兜底（挡住历史 manifest）。素材找不到时不再笼统报「素材不足」，
而是明确列出缺哪些文件。

### 9.2 根因二：`config.log_success` 不存在 —— **画质越好越会崩**

`pipeline/train_gsplat.py` 在训练末尾按 PSNR 打分：

```python
if mean_psnr >= 28:      config.log_success(...)   # ← config 里根本没有 log_success
elif mean_psnr >= 24:    config.log_success(...)   # ← 同上
elif mean_psnr >= 20:    config.log_warn(...)      # ← 这个存在
```

`log_success` 在 `pipeline/config.py` 里**从未定义**。后果非常反直觉：
PSNR < 24 dB（画质差）能正常收尾，PSNR ≥ 24 dB（画质好）在**评估跑完、PLY 还没保存**
时抛 `AttributeError`，整个任务以退出码 5 失败。

实测证据（同一份素材阶梯，7000 步）：

| 素材 | 帧数 | 平均 PSNR | 结果 |
| --- | --- | --- | --- |
| 12.0 MB | 23 | 20.95 dB | ✅ 正常产出 PLY |
| **16.0 MB** | 28 | **25.10 dB** | ❌ `AttributeError: module 'config' has no attribute 'log_success'` |
| 24.0 MB | 43 | 20.38 dB | ✅ 正常产出 PLY |

修复：调用点改为 `log_ok`，并在 `config.py` 里保留 `log_success = log_ok` 别名兜底。

### 9.3 根因三：「取消」关不掉（两条独立路径都不可靠）

用户反馈「在开始建模子界面中，点击取消无法正常关闭窗口」。实测两条路径都有问题：

| 路径 | 问题 |
| --- | --- |
| 对话框的「取消」 | 只依赖 `<form method="dialog">` 的**默认提交行为**。一旦这条默认行为被阻断（内核不支持/被其它处理器 `preventDefault`），窗口就关不掉 |
| 建模进行中的「取消」 | 用的是 `window.confirm`。原生弹窗在部分环境/嵌入式内核里会被**静默屏蔽**，表现为「点了毫无反应」—— 与上一轮「导入的视频删不掉」是同一个坑 |

修复（两条都改成不依赖原生行为）：

- `ui.js` 新增 `openDialogModal / closeDialogModal / ensureDialogClosable`：
  捕获阶段监听，`data-dialog-close` / `value="cancel|close"` / 文案为「取消/关闭」
  的按钮**一律显式关窗**；内核没有 `<dialog>` 时退化为 `open` 属性 + CSS 兜底渲染。
- 建模任务取消、标注删除改为自定义确认框 `ui.confirm()`。

测试里同时给出**基线复现**（证明这条默认路径确实会被阻断）与**修复后断言**：

```
[OK] 基线复现：submit 被阻断时，form method=dialog 确实关不掉窗口   这正是「点取消关不掉」的机制
[OK] 取消 submit 默认路径后，「取消」依然能关闭对话框                {"openedAttr":true,"closedAttr":true,"openProp":false}
[OK] 内核没有 <dialog> 时也能打开窗口（兜底渲染）
[OK] 不再使用 window.confirm（原生弹窗被屏蔽也不会「毫无反应」）
```

### 9.4 根因四：工作区迁移不完整（F 盘实例其实还在用 C 盘的依赖）

`pyruntime312\python312._pth`（内嵌 Python 的模块搜索路径）里写的是**绝对路径**：

`pyruntime310\python310._pth` 同样问题。

修复：改成**相对路径** `..\pydeps312` / `..\pydeps`，从此与盘符无关。

### 9.6 根因五（端到端验证时才暴露）：一键流水线默认用了「更差」的匹配策略

用真实 175 帧素材把 Web 链路整条跑一遍时，COLMAP 报：

```
COLMAP 特征匹配：colmap.exe sequential_matcher …（24.8 秒）
重建完成：注册 57/175 张图片（32.6%），稀疏点 11920 个
[错误] 注册成功的图片太少：57/175（要求 ≥60% 且 ≥8 张）
```

同一份 175 帧素材，用 exhaustive 匹配在**上一轮已经验证过 178/178（100%）注册**。
原因是 `colmap_recon.py` 的 `--matcher auto` 对「文件名形如 `frame_XXXX`」的输入
**优先选 sequential**，而 `重建流水线.bat` 正好不带 `--matcher` 参数。
而日志给出的补救建议第 4 条还写着「视频帧改用顺序匹配（…对连续视频更稳）」——
**实测数据正好相反**：手持现场视频常常边走边回头，顺序匹配会把回环漏掉。

修复两条：

1. `choose_matcher` / `print_remediation` 的措辞改为实测结论，不再推荐无脑用 sequential；
2. **注册率不达标时自动用 exhaustive 重试一次**（保留 sequential 的速度优势，
   又不会让用户白等一场）。重试会先清掉上次的 `sparse/`，避免捡到差模型；
   `pycolmap` 若已确认不可用则不再重复尝试。
