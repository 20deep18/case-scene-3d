# 现场建模与精确测量功能说明

> 本文件说明本轮新增的两组**核心业务功能**：
> 1. **依据视频和图片建立现场模型**（Web 端一键建模）
> 2. **精确测量闭环**：粗模上标记「需精确测量的位置」→ 民警实测填写 → 反算比例尺提升精度

---

## 一、依据视频和图片建立现场模型

### 1.1 在界面上的位置

左侧面板「案件」区下方新增 **「现场建模」** 区块：

```
┌ 现场建模 ────────────────────────┐
│ 依据本案导入的视频/图片建立现场三维模型。  │
│ 流程：抽帧 → COLMAP 位姿 → 高斯泼溅训练  │
│      → 导出 .splat                     │
│                                   │
│      [ 开始建模 ]                  │
│                                   │
│  现场建模 ▓▓▓▓▓▓░░░░░░  62%        │
│  高斯泼溅训练 · 已用时 4 分 12 秒     │
│  [查看日志]  [取消]                │
└───────────────────────────────────┘
```

### 1.2 使用步骤

1. 先在右下角 **「+ 导入监控/勘查视频」** 上传现场视频或照片
   （它们会挂到本案的「相机」标注上，成为建模素材）
2. 点 **「开始建模」** → 弹出参数对话框，显示将要使用的素材清单
   **与素材体积体检结论**（合计多少 MB / 实测建模下限多少 MB / 是否充足）
3. 确认模型名称（默认「<案件名> 现场模型」）与参数 → **「开始建模」**
   - 体积 **≥ 实测下限** → 直接开跑，不再多问
   - 体积 **< 实测下限** → 先弹「**提供信息过少，可能无法正常建模**」，
     由用户选择「仍然开始建模」或「取消」（取消后对话框保持打开，方便去补素材）
4. 左侧进度条实时显示四个阶段：**抽帧 → COLMAP 位姿 → 高斯泼溅训练 → 导出**
5. 完成后自动刷新「模型文件」下拉，选中新模型点 **「载入三维现场」** 即可

### 1.2.1 素材体积门槛（实测求得）

体积本身不是物理量，但它在本系统里是「素材够不够」的一个**可测量代理**：
同一台设备同一编码参数下，体积 ≈ 时长，而时长在固定抽帧帧率下决定**可用视角数**；
视角数不足 → COLMAP 注册不上 → 点云太稀 → 高斯泼溅没有足够约束 → 模型糊掉或直接失败。

阈值由 `tools/threshold_experiment.py` **跑真实训练**求得（见
[`docs/建模最小素材体积实测.md`](建模最小素材体积实测.md)）。当前口径：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `minBytes` | 见 `pipeline/recon_threshold.json` | 实测中**首次跑出可用模型**的素材体积 |
| `recommendedBytes` | 同上 | 舒适区（建议值） |

⚠️ **这不是充分条件**：同样的体积，拍摄质量（是否有真实平移、画面是否有纹理）
决定成败 —— 实测里 32 MB 那一档就因为该段视频以旋转为主、注册率只有 53% 而失败。
所以系统**只提示、不禁止**：用户永远可以点「仍然开始建模」。

`materials` 的返回（前端据此决定「直接建模」还是「先提示」）：

```json
{
  "ok": true,
  "count": 2, "videos": 1, "images": 1,
  "bytes": 128233647,
  "files": [{ "name": "现场勘查（东侧）视频 01.mp4", "kind": "video", "bytes": 117747992 }],
  "missing": [],
  "minBytes": 12582912,
  "recommendedBytes": 33554432,
  "enough": true,
  "threshold": { "measured": true, "measuredAt": "2026-10-05", "report": "output/threshold/threshold-report.md" }
}
```

> **中文文件名的坑（这是「开始建模点了没反应」的根因）**：
> 上传接口把文件名编码进 URL（`/media/<pid>/media/%E7%8E%B0%E5%9C%BA.mp4`）。
> 服务端此前直接把这串字符当磁盘路径，拿到的是**字面量 `%E7%8E%B0…`** 这种不存在的文件，
> 于是流水线报「视频不存在 → 可用图片 0 张 → **素材不足**」——
> 用户看到的是「素材不够」，真相却是路径没解码。
> 现在 `mediaFileNameFromUrl()` 统一解码，`recon_job.py` 里还留了一层
> 「解码后重试」的兜底（挡住历史 manifest）。

**进度协议**：Python 编排脚本在每一步打印机器可解析的标记

```
[阶段] extracting|0.030|整理素材（视频抽帧 / 图片归集）
[阶段] reconstructing|0.100|COLMAP 位姿重建（175 张图）
[阶段] training|0.380|高斯泼溅训练（30000 步）
[阶段] converting|0.930|导出 .splat 并登记到模型库
[阶段] done|1.000|建模完成：xxx.splat（1.8 MB）
```

服务端 `refresh()` 只取**最后一条**阶段标记（避免早期日志覆盖当前状态），
前端每 1.5 秒增量拉取日志，所以刷新页面也能接回正在跑的任务。

### 1.5 三个关键工程约束（本机实测）

1. **服务端没有 torch/gsplat**
   Node 的 embeddable 运行时不带这些库，训练必须在 `pyruntime312` 环境 +
   MSVC v143 + CUDA 12.8 下执行。
   所以统一通过 `tools/msvc-env.bat` 包一层 cmd 来调 Python。
   详见 [gsplat环境搭建与编译.md](gsplat环境搭建与编译.md)。

2. **子进程输出重定向到文件描述符，而不是管道**
   DSH 受限模式下程序不能开命名管道。虽然本机实测 `stdio:'pipe'` 也能用，
   但为了稳妥（也让 Web 端能随时拉完整日志、刷新不丢进度），
   把 stdout/stderr 重定向到 `fs.openSync` 得到的 fd，日志落盘到
   `<jobDir>/pipeline.log`，对外只暴露「读文件」这一条路径。

3. **同一时间只允许一个建模任务**
   8 GB 显存不适合并发训练，抽帧也吃 CPU。第二个请求会返回 409 并说明原因。

### 1.6 退出码约定（会翻译成中文提示）

| 码 | 含义 |
| --- | --- |
| 0 | 成功 |
| 2 | 参数/素材错误（图片少于 8 张等） |
| 3 | 缺少 torch / gsplat |
| 4 | 显存不足（建议调大 downscale） |
| 5 | 训练失败 |
| 6 | COLMAP 注册率不达标（建议重拍素材） |

## 二、精确测量闭环

### 2.1 业务需求对应

| 需求 | 实现 |
| --- | --- |
| 民警可以测定房间的准确数据并上传，使建模更精确 | 「📏 尺寸标注」工具 + 「待测清单」填写表单 + 「按实测量校正」按钮 |
| 在粗略建模文件里标注哪里需要精确数据 | 尺寸标注以**红点 + 红线 + 红色标签「待民警实测」**画在三维现场上 |
| 民警测量后直接填写 | 属性面板里的实测输入框，或「待测清单」里批量填写；另支持导出 CSV 打印带去现场 |

### 2.2 工作流

```
① 技术人员在粗模上操作
   工具栏 → 📏 尺寸标注 → 点两个端点
   生成一条 dimension 标注（measured = null）

② 现场民警测量
   左侧「精确测量」→「待测清单 / 填写」
   对照屏幕上的红点/红线位置，用卷尺量出真实距离并填写
   （也可点「导出 CSV」打印带去现场）

③ 系统反算比例尺
   点「按实测量校正」
   后端最小二乘求解 → 写入 project.world.scaleToMeters
   整个模型与所有测距立刻按真实尺寸显示
```

### 2.3 比例尺反算的数学原理

设模型单位到米的换算为 `s`，对每条已实测的尺寸 `i`：

```
s · d_model,i  ≈  d_real,i
```

最小二乘最优解（过原点）：

```
s* = Σ(d_model,i · d_real,i) / Σ(d_model,i²)
```

同时输出**逐条残差**与**RMS / 平均相对偏差**，并按阈值给出可信度：

| 平均相对偏差 | 可信度 | 建议 |
| --- | --- | --- |
| < 2% | high | 可用于精确测距 |
| 2% ~ 5% | medium | 可用，建议补测 |
| > 5% | low | **建议复核标注点是否点准** |

> 只解**尺度**（1 个自由度）。模型与现场只差一个尺度（重建的比例是被任意定的），
> 不需要解旋转/平移。若测量里混入端点拾取误差，`s*` 会被平均掉 ——
> 这正是要给出逐条残差的原因。

### 2.4 界面上能看到什么

**三维现场里**：

- 待测：**红色**端点球 + 红色直线 + 标签「尺寸标注 / 待民警实测 / 模型 X.XXX m」
- 已测：**绿色**端点球 + 绿色直线 + 标签「实测 X.XXX m / 模型 X.XXX m（差 ±X.XXX m）」

**左侧「精确测量」区**：待测项数徽标（有待测时变红）、比例尺与校正状态

**待测清单对话框**：
- 上半部分：待测项（编号、名称、优先级「必测/常规/可缓」、模型侧距离、填写框）
- 下半部分：已实测项（显示偏差与测量人，可修改后重新校正）
- 顶部按钮：**导出 CSV（打印带去现场）**
- 底部按钮：**保存全部**

**右侧属性面板**（选中一条尺寸标注时）：模型侧距离、民警实测、偏差、测量人、
实测输入框、「提交实测值」与「按实测校正比例尺」按钮

### 2.5 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/projects/:id/measurements` | 待测清单 + 已测清单 + 当前比例尺与校正信息 |
| POST | `/api/projects/:id/calibrate` | 反算比例尺（`apply:false` 只算不写回） |

尺寸标注走标准的标注接口（`kind: 'dimension'`）：

```json
{
  "kind": "dimension",
  "label": "客厅东西向净宽",
  "points": [[-1.5, 1.0, -2], [1.5, 1.0, -2]],
  "modelDistance": 3.0,
  "measured": null,          // null = 待实测；填数字即已实测
  "unit": "meter",
  "priority": "high",        // low | normal | high
  "note": "沿踢脚线量"
}
```

服务端会自动补 `pending`、`measuredBy`、`measuredAt` 字段。

## 四、顺带修掉的两个既有问题

1. **模型库的「高斯数量」永远显示未知**
   服务端读的是 `meta.count`，而 `to_splat.py` 写的是 `gaussianCount`，
   字段名不一致。现按 `gaussianCount → count → gaussians` 依次兜底。
   修复后界面能正确显示「59,919 高 斯」而不是空白。

2. **校验类错误一律报 500**
   `store.normalizeAnnotation` 抛的是用户输入错误（例如尺寸标注只给了一个端点），
   却报成 500 服务端故障。现在带 `statusCode` 的错误会正确返回 400。
