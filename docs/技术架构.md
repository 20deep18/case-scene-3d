# 技术架构

本文说明系统内部的坐标系、数据流、渲染管线与协同协议，供二次开发与排错参考。

---

## 一、坐标系（最容易踩坑的地方）

系统里同时存在 **3 套坐标系**，代码中已集中处理，不要在各处自行换算。

### 1. COLMAP / 3DGS 世界系（代码里叫 local）

```
x 向右   y 向下   z 向前
```

- COLMAP 的 `cameras.bin` / `images.bin` / `points3D.bin` 全部使用这套系
- 3DGS 训练出的 `.ply` / `.splat` 的坐标也在本系
- **所有标注数据**（`annotations[].points`、`annotations[].pose`）一律存储在本系

相机模型：`x_cam = R · x_world + t`，相机看向 `+z`，相机中心 `C = -Rᵀ t`。
四元数顺序为 `(w, x, y, z)`（COLMAP 与 3DGS 一致）。

### 2. Three.js 场景系（代码里叫 scene）

```
x 向右   y 向上   z 向后
```

换算关系（`app/web/js/camera-overlay.js` 中唯一出处）：

```js
WORLD_QUAT   = Quaternion().setFromAxisAngle(X轴, -Math.PI/2)
WORLD_MATRIX = Matrix4().makeRotationFromQuaternion(WORLD_QUAT)
// local -> scene:  p_scene = WORLD_MATRIX · p_local  ；q_scene = WORLD_QUAT · q_local
// scene -> local:  p_local = WORLD_MATRIX⁻¹ · p_local；q_local = WORLD_QUAT⁻¹ · q_scene
```

> **注意**：`R_x(-90°)` 的实际效果是 `(x,y,z)_local → (x, z, -y)_scene`，即 **y/z 两轴互换**。
> 因此 local 系的「世界上方向」对应 `[0, 0, 1]`，而不是 `[0, -1, 0]`。
> 位置与姿态都用同一个矩阵换算，所以前后向语义自洽、publish/receive 严格互逆。

### 3. 屏幕系

像素坐标 `(u, v)`，原点左上，与图像行号方向一致。

## 二、相机姿态的表示（`pose`）

监控/勘查相机在数据库里存为一个 `kind: "camera"` 的标注，其 `pose` 字段：

```jsonc
{
  "source": "pnp" | "manual" | "manual-drag",   // 来源
  "frame": "gaussian",                          // 固定为 3DGS 世界系
  "position": [x, y, z],                        // 机位（local 系）
  "target":   [x, y, z],                        // 画面中心朝向点（与 rotation 二选一）
  "rotation": [9 个数],                          // 行优先旋转矩阵（优先级高于 target）
  "up":  [0, 0, 1],                             // 相机上方向（local 系）
  "fovY": 45,                                    // 垂直视场角（度）
  "aspect": 1.777,                               // 画面宽高比
  "intrinsics": { "fx":..., "fy":..., "cx":..., "cy":..., "width":..., "height":..., "dist":[...] },
  "reprojectionError": 0.42                      // PnP 解算的重投影误差（像素）
}
```

**渲染时的语义**：该 pose 被用作一个 `THREE.Group` 的姿态，**Group 的局部 -Z 轴就是观察方向**
（视频四边形放在局部 `z = -far` 处）。从 pose 到四元数的唯一实现在
`camera-overlay.js` 的 `annotationPoseToLocalQuaternion()`：

```
right = normalize(f × u)      f = target - position，u = pose.up
up    = normalize(right × f)
基的三列 (X, Y, Z) = (right, up, -f)
```

`flyTo()` 返回可直接赋给 `THREE.PerspectiveCamera` 的四元数（该相机同样朝局部 -Z、上为 +Y）。

## 三、数据流

```
手机/执法记录仪视频
      │  pipeline/extract_frames.py（ffmpeg 抽帧 + 拉普拉斯模糊过滤）
      ▼
   frame_*.png
      │  pipeline/colmap_recon.py（COLMAP / pycolmap：特征 → 匹配 → 增量式 SfM）
      ▼
 sparse/0/{cameras,images,points3D}.bin
      │  pipeline/train_gpu.py（纯 PyTorch GPU 高斯泼溅训练）
      │    或 pipeline/train_gsplat.py（有 gsplat 时）
      ▼
 point_cloud.ply（标准 3DGS 格式）
      │  pipeline/to_splat.py（32 字节/高斯，量化，去噪，抽稀）
      ▼
 data/models/scene.splat + scene.json
      │  Node 后端 /models/index.json 自动索引
      ▼
 浏览器自研 WebGL2 渲染器 → 三维现场
      │  在场景里点选 3D 点 ↔ 监控画面像素点
      ▼
 app/web/js/pnp.js（DLT + Hartley 归一化 + LM 精修）→ pose
      ▼
 视频按该 pose 贴回三维现场，浏览器验证重合
```

## 四、Web 端 3DGS 渲染管线

`app/web/js/splat-renderer.js` 是本项目自研的 WebGL2 渲染器，实现要点：

| 环节 | 做法 |
| --- | --- |
| 数据格式 | `.splat`：每个高斯 32 字节（位置 3×f32、线性尺度 3×f32、RGBA 4×u8、四元数 4×u8） |
| 顶点着色器 | 把 3D 协方差 `Σ = R S Sᵀ Rᵀ` 经 `W`（视图旋转）与 Jacobian `J` 投影成 2D 协方差，求逆得 conic（椭圆二次型） |
| 片元着色器 | `exp(-0.5 · 二次型)` 还原高斯衰减，`gl_PointCoord` 直接给出椭圆内归一化坐标 |
| 走样消除 | 对角项加 `+0.3` 低通，等价于 3DGS 论文中对 2D 协方差加 0.3 的膨胀 |
| 深度排序 | 每帧按视深度对每个「块」做 **LSD 基数排序**（8 位 × 4 趟），远 → 近；块大小 40 万高斯 |
| 混合 | 预乘 alpha：`blendFuncSeparate(ONE, ONE_MINUS_SRC_ALPHA, ...)`，关闭深度测试与写入 |
| 球谐 | 支持 SH0；数据带 `f_rest_*` 时可开启 SH1/SH2（编译期 `#define USE_SH`） |
| 拾取 | 高斯点云没有三角面，用「均匀网格索引 + 射线最近点 + K 近邻 PCA 法向」估计表面点（`picker.js`） |

性能参考（RTX 5060 Laptop，12 万高斯，960×540）：排序 + 绘制稳定 60 FPS。

## 五、协同协议（WebSocket）

连接：`ws://<host>:<port>/ws?project=<案件ID>&name=<昵称>&color=<颜色>&role=<角色>`

服务端 → 客户端：

| 消息 | 含义 |
| --- | --- |
| `welcome` | 连接成功：`{you, project, roster}` |
| `roster` | 在线名单变化 |
| `pose` | 某人的视角更新 `{id, p, q, fov, mode}` |
| `cursor` | 某人的光标位置 |
| `chat` | 文字消息 |
| `annotation.add/update/delete/batch` | 标注变更（含 `by` 字段标识操作人） |
| `system` | 系统提示（加入/离开） |
| `error` | 错误 |

客户端 → 服务端：

| 消息 | 含义 |
| --- | --- |
| `pose` | 上报视角（前端节流 12Hz） |
| `select` | 上报当前选中对象 |
| `chat` | 发消息 |
| `annotation.add/update/delete/batch` | 提交标注变更 |
| `ping` | 心跳（带时间戳，用于测延迟） |

设计取舍：
- **服务端权威**：所有写操作经服务端校验（`store.js` 的 `normalizeAnnotation`）后落盘，再广播
- **最后写入生效**：每条标注带 `updatedAt`，冲突时以到达顺序为准；`revision` 单调递增用于增量拉取
- **视角不走存储**：`pose` 只广播不落盘，避免大量无意义写入

## 六、水平扩展建议（当前为单机）

当前实现刻意保持**零外部依赖**（不需要 npm install、不需要数据库），适合单派出所/单案组部署。
要扩展到多节点，按以下顺序改造：

1. **会话外置**：把 `app/server/index.js` 里的 `rooms` Map 换成 Redis Pub/Sub，多个 Node 进程共享房间
2. **存储外置**：把 `store.js` 的文件写入换成 SQLite（单机）或 PostgreSQL + PostGIS（多机，可直接用 SQL 做空间查询）
3. **模型分发**：`.splat` 目前由 Node 静态服务，多节点时建议放对象存储 + CDN，并开启 Range 请求（已支持）
4. **训练队列**：把 `pipeline/` 的脚本接一个任务队列（如 Redis Queue），现场采集后异步排队重建
5. **鉴权**：当前无登录，接入警务统一身份认证后，在 WebSocket 握手与 REST 前置一层校验，并把 `operator` 换成真实警号
