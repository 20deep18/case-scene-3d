## 零、两个致命 bug（这轮画质问题的真正原因）

这一轮在真实素材上暴露了**两个**此前一直存在、但在合成数据上被掩盖的致命 bug。
它们合起来解释了「为什么模型一直是糊的/黑的/霓虹色」。

### bug A：PLY 数据区写成了「块主序」而不是「记录主序」（最致命）

PLY 的数据区必须按**记录主序（record-major）**排列：

```
高斯1.x  高斯1.y  高斯1.z  高斯1.f_dc_0 ... 高斯1.rot_3
高斯2.x  高斯2.y  高斯2.z  高斯2.f_dc_0 ... 高斯2.rot_3
...
```

而 `save_ply` 原来是**块主序（block-major）**：

```python
for block in blocks:          # ✘ 错
    handle.write(tensor_block_to_bytes(block, numpy))
# 写出的是：所有高斯的 x、所有高斯的 y、……、所有高斯的 rot_3
```

后果：**整个 PLY 对任何标准读取器都是错位的**。典型指纹是所有字段的
统计量几乎一样（因为每个字段都横跨了整块数据的范围）：

| 字段 | 修复前 | 应为 |
| --- | --- | --- |
| `x` | min -8.4 中位 -0.7 max 4.2 | 位置（米） |
| `f_dc_0` | min -8.35 中位 0.001 max **10.23** | SH 直流，约 -2~2 |
| `opacity` | min -7.66 中位 0.001 max **9.95** | logit，约 -8~5 |
| `scale_0` | 中位 **4.10** | 线性米，约 0.001~0.3 |
| `rot_0` | **3.89**（四元数分量不可能 >1） | 约 -1~1 |

**表现**：在浏览器里加载 `.splat` 后是一堆**霓虹色大色块**；而训练进程内直接渲染
（不经过 PLY）却是正常的 —— 这就是为什么之前所有"渲染对比图"看着都还行，
一放到 Web 端就完全不对。

**修复**：按列拼成一个 `(N, D)` 矩阵再整体按行写出，并加了列数一致性断言：

```python
table = torch.cat([b.reshape(count, -1) for b in blocks], dim=1).contiguous()
if table.shape[1] != len(names):
    raise RuntimeError(f"PLY 属性数与数据列数不一致：header {len(names)} 列，数据 {table.shape[1]} 列")
handle.write(tensor_block_to_bytes(table, numpy))
```

**修复后的字段分布（已用 `tools/verify_ply_layout.py` 验证各自独立且物理合理）**：

```
x        min -8.4242  中位 -0.7331  max  4.2293
y        min -4.0050  中位  0.3244  max  7.7682
z        min -7.7335  中位 -0.1669  max 17.1491
f_dc_0   min -1.7738  中位  0.8003  max  2.2301   ✔ 合法 SH 直流
opacity  min -6.3484  中位 -3.9781  max  4.5957   ✔ legal logit
scale_0  min  0.0001  中位  0.0392  max  0.3408   ✔ 线性米
rot_0    min  0.1515  中位  0.8423  max  1.6686   ✔ 四元数分量
```

> `scale_0` 的上限 0.3408 正好等于 `0.05 × 6.816 = 0.3408` ——
> 说明 `_clamp_scales` 的尺度夹紧**一直在正确工作**，
> 之前看到的"82% 超过 1 米"完全是错位文件造成的假象。

### bug B：不透明度重置撞上训练末尾

这是**第二个**独立 bug，同样致命。

#### 现象

在真实素材上训练，**训练视角**的渲染结果：

| 训练步数 | alpha 均值 | 渲染均值 | 真值均值 | 状态 |
| --- | --- | --- | --- | --- |
| **400 步** | **0.930** | 0.338 | 0.340 | 正常 |
| **15000 步** | **0.033~0.151** | 0.024~0.091 | 0.34~0.62 | **几乎全黑** |

训练越久反而越黑，非常反直觉。

#### 根因

```python
if args.opacity_reset_interval > 0 and iteration % args.opacity_reset_interval == 0:
    self.reset_opacity(iteration)      # 把所有 opacity 打到 0.005
```

默认 `opacity_reset_interval = 3000`，而训练总步数是 15000 ——
**15000 正好是 3000 的整数倍**，于是：

1. 第 15000 步触发重置，所有高斯不透明度被压到 0.005；
2. 训练循环**随即结束**；
3. 保存的就是这个"刚被清空"的模型。

不透明度从 0.005 恢复需要几百步，但已经没有后续迭代了。

#### 修复

临近结束时不再重置，留出最后 10%（至少 500 步）让不透明度沉淀：

```python
tail = max(500, int(args.iterations * 0.1))
if iteration <= args.iterations - tail:
    self.reset_opacity(iteration)
```

#### 效果（同一素材、同样 15000 步）

这是**最隐蔽也最严重**的一个 bug，它同时解释了合成数据与真实数据两次"画质上不去"。

### 现象

在真实素材上训练 15000 步，**训练视角**的渲染结果：

| 训练步数 | alpha 均值 | 渲染均值 | 真值均值 | 状态 |
| --- | --- | --- | --- | --- |
| **400 步** | **0.930** | 0.338 | 0.340 | 正常 |
| **15000 步** | **0.033~0.151** | 0.024~0.091 | 0.34~0.62 | **几乎全黑** |

训练越久反而越黑，这非常反直觉。

### 根因

`pipeline/train_gsplat.py` 的周期性不透明度重置逻辑：

```python
if args.opacity_reset_interval > 0 and iteration % args.opacity_reset_interval == 0:
    self.reset_opacity(iteration)      # 把所有 opacity 打到 0.005
```

默认 `opacity_reset_interval = 3000`，而训练总步数是 15000 ——
**15000 正好是 3000 的整数倍**，也就是说：

1. 第 15000 步触发重置，所有高斯的不透明度被压到 0.005；
2. 训练循环**随即结束**；
3. 保存的就是这个"刚被清空"的模型。

不透明度从 0.005 恢复到正常需要几百步，但已经没有后续迭代了。
于是导出的模型 alpha 只有 0.03~0.15 —— 渲染出来几乎全黑。

### 效果（同一素材、同样 15000 步）

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 留出视角 PSNR | **6.74 dB** | **18.02 dB** |
| 留出视角 SSIM | 0.1805 | **0.7688** |
| 渲染 alpha 均值 | 0.03~0.15 | 正常 |

> **这个 bug 同样影响了前面几轮合成数据的结论**（v2/v3/v4 的 20 dB 上限）——
> 那几轮的 7000 步同样触发了"最后一次重置"，所以真实上限比当时测的更高。
> 这也是为什么"提高分辨率反而更差"：噪声数据下重置的伤害被掩盖了。

### 教训（这两个 bug 合起来给的）

**1）导出格式必须用独立读取器交叉验证。**
PLY 块主序的错误在**训练进程内完全看不出来**（内存里的参数是对的），
只有把文件写出去、再用**另一套代码**读回来才会暴露。
本次是靠"在浏览器里加载 .splat 看到霓虹色块"才发现的。
现已加入 `tools/verify_ply_layout.py`：用结构化 dtype + `end_header` 字节偏移
逐字段检查分布是否**各自独立且物理合理**（四元数分量必须在 -1~1，
不透明度是 logit，尺度是米）。**看到"所有字段统计量雷同"就要立刻怀疑错位。**

**2）周期性重置类操作必须避开训练末尾。** 这类 bug 的特征是
"训练 loss 很低但渲染结果很糟"，因为 loss 是在重置**之前**的迭代上算的。
诊断方法是**直接渲染训练视角并检查 alpha 均值** ——
只 loss 或只看留出视角都不足以发现它。

| 步骤 | 结果 |
| --- | --- |
| 抽帧 2fps / 长边 1600 | 212 帧 |
| 模糊过滤（拉普拉斯阈值 60） | 保留 **175**，剔除 37 |
| 硬切检测（`tools/detect_cuts.py`） | 只有 **1 处**硬切（第 107 帧附近） |

### COLMAP：顺序匹配 vs 穷举匹配（决定性差异）

| 匹配方式 | 注册图片 | 稀疏点 | 重投影误差 | 耗时 |
| --- | --- | --- | --- | --- |
| `sequential` | **61 / 175（34.9%）** | 9,684 | 0.672 px | 1 分 42 秒 |
| **`exhaustive`** | **178 / 175（100%）** | **61,874** | 1.067 px | 10 分 58 秒 |

**穷举匹配把注册率从 35% 拉到 100%，稀疏点从 9.7k 提到 61.9k（6.4 倍）。**
这是本次画质提升最关键的单一改动。

> 为什么会这样：视频是**原地转圈拍摄**，相邻帧虽然有重叠但基线极短；
> 顺序匹配只比相邻帧，能提供的三角化约束很弱，重建中途就断了。
> 穷举匹配让**任意两帧**都能配对，远距离（大基线）的帧对提供了真正有效的三角化。
>
> **经验**：视频素材不要默认用 sequential。先跑一次 exhaustive（哪怕慢 10 倍），
> 注册率会明显不同。帧数很多（>500）时再考虑 sequential + loop closure。

### 为什么仍有可见模糊（诚实说明）

**根本原因：这段视频是"原地转圈"，相机几乎没有平移。**

- 纯旋转拍摄**没有视场基线（baseline）**，三角化几何先天病态，
  深度只能靠先验猜 → 高斯被拉大、表面发糊。
- 这不是软件缺陷：任何 SfM/3DGS 系统在纯旋转素材上都会这样。
- 次要因素：训练用 downscale 2（450×800），细节分辨率有限。

**要进一步提升画质，唯一有效的做法是改变拍摄方式**（见最后一节）。

## 三、为什么 PSNR 只有约 20 dB —— 素材决定了上限

这是**唯一重要**的解释，有量化证据。

### 3.1 素材本身接近随机噪声

用 `tools/texture_difficulty.py` 度量：如果只用**一张纯色**（该图自身均值）去预测，
能得到多高的 PSNR？

| 视角 | 常量图 PSNR | 相邻像素平均差 |
| --- | --- | --- |
| view_001 | 12.96 dB | 28.3 |
| view_004 | 12.28 dB | 29.6 |
| view_008 | 10.90 dB | 31.9 |
| **平均** | **13.81 dB** | 28~32 |

相邻像素差 28~32 是**白噪声量级**。也就是说这套合成纹理在三维空间里近似随机噪声 ——
它对 SIFT 是理想输入（特征点 3152/张，所以 COLMAP 才能 100% 注册），
但对 3DGS 是**最坏输入**：没有任何可复用的低频结构。

### 3.2 在噪声上"提分"很有限

| 方法 | PSNR |
| --- | --- |
| 只用平均色（什么都不学） | 13.81 dB |
| **3DGS 7000 步** | **19.78 dB** |
| 3DGS 论文在 Mip-NeRF360 等真实场景 | 27~28 dB |

3DGS 比"什么都不做"高出 **6 dB**，说明它确实在重建结构；
但要在白噪声上达到 27 dB 是不可能的 —— 那需要逐像素记住随机图案。

### 3.3 提高分辨率反而更差

| 训练分辨率 | PSNR |
| --- | --- |
| downscale 1（960×540） | 18.97 dB |
| downscale 2（480×270） | **20.29 dB** |

分辨率越高，需要拟合的高频噪声越多，PSNR 反而下降 —— 这是"素材是噪声"的又一佐证。

**真实照片（墙面、地板、家具的低频结构为主）不会出现这个现象**，
提高分辨率通常会明显提升画质。

## 四、这一轮修掉的真 bug

跑通训练的过程中暴露出 4 个真问题，全部已修复：

### 4.1 `/Wno-attributes` 传给 MSVC（致命）

`gsplat/cuda/_backend.py` 无条件给 C++ 编译加了 GCC 风格的 `-Wno-attributes`：

```
cl: 命令行 error D8021 :无效的数值参数"/Wno-attributes"
```

后果是**所有 `.cpp`（Null/Adam/Intersect/Projection/ext…）全部编译失败**。
改成 `if os.name != "nt"` 才加。

### 4.2 `_jit_compile` 签名不匹配

torch 2.7.1 的签名是
`(name, sources, extra_cflags, extra_cuda_cflags, extra_syncl_cflags, extra_ldflags, …)`，
比 gsplat 预期多一个**位置参数**。gsplat 的位置传参让 `verbose` 落到
`extra_sycl_cflags` 上，报：

```
TypeError: _jit_compile() missing 2 required positional arguments: 'verbose' and 'with_sycl'
```

改为 `inspect.signature()` 读真实签名 + 关键字传参。

### 4.3 致密化阈值被错误放大（画质主因之一）

`pipeline/train_gsplat.py` 里写的是：

```python
threshold = self.args.densify_grad_threshold * self.spatial_scale   # ✘
```

**梯度阈值不能乘场景尺度** —— 3DGS 的 `2e-4` 是位置参数梯度范数的**绝对**阈值。
本场景 `spatial_scale = 6.202`，等于把阈值抬高 6.2 倍，导致几乎没有高斯能达标：

| | 致密化前 | 修复前 7000 步 | 修复后 7000 步 |
| --- | --- | --- | --- |
| 高斯数量 | 10,849 | **11,045**（几乎没长） | **34,230** |

学习率乘 `spatial_scale` 是对的（不同量纲），阈值不是。

### 4.4 PLY 的 scale 约定写错（互操作性致命）

3DGS 官方 PLY 里 `scale_*` 存的是**线性尺度**（已激活）。而 `save_ply` 直接写了
`scales_log`，于是：

- 外部标准 3DGS 查看器会对它**再取一次 exp** → 尺度全部变成 ~1.0 的巨球；
- 本项目的 `to_splat.py` 按标准约定会 exp 一次（它是对的），
  所以自家人能跑通、但产物对外不兼容。

修复：`save_ply` 写 `torch.exp(scales_log)`；
同时给 `to_splat.py` 增加 `--scales-are-log` 开关以兼容旧产物。

**修复前后对比**（同样是 train → to_splat）：

| | 转换保留率 | 包围盒半径 |
| --- | --- | --- |
| 修复前 | 5,879 / 49,313 = **12%** | 17.79 m（场景实际约 7 m） |
| 修复后 | 30,222 / 34,230 = **88%** | **6.77 m** ✔ |

### 4.5 顺带：`_clamp_scales` 尺度夹紧

尺度学习率按场景尺度放大后没有硬上限，参数会单调涨到十几米。
新增 `_clamp_scales()`（上限 `0.1 × spatial_scale`，与剪枝阈值一致），每步执行。

## 六、结论与下一步

### 能做什么

**现在这套流程已经可以用于真实拍摄素材**：

```bat
call tools\msvc-env.bat
python pipeline\train_gsplat.py --data <COLMAP 场景目录> --out <输出目录> ^
    --iterations 30000 --downscale 2 --sh-degree 3 --eval-views 4
python pipeline\to_splat.py --ply <输出目录>\point_cloud.ply --out data\models\<名称>.splat
```

### 距离"人类可读的高保真模型"还差什么

**第一因素：素材。** 需要真实拍摄的照片/视频（有低频结构、适度纹理、充分重叠），
而不是程序生成的噪声纹理。这一点已经量化证明（第 3 节）。

**第二因素：迭代次数。** 本次只跑 7000 步（49 秒）。3DGS 论文用 30000 步；
7000 步大约是"能看出形状"的水平。30000 步约 3.5 分钟，可直接跑。

**第三因素：分辨率。** 8 GB 显存下 `downscale 2`（480×270）是稳妥档；
真实素材上可以试 `downscale 1`（960×540），本次实测约 92 秒。

**不构成限制的**：gsplat 本身的实现质量。官方 CUDA 内核已经跑通并用上了。

### 建议的下一步

**1. 改用「走位」拍摄（这是画质的关键，比任何参数都重要）**

这段素材最大的问题是**原地转圈**。请这样拍：

| 要点 | 说明 |
| --- | --- |
| **边走边拍** | 沿房间走一圈（例如绕床走），相机位置要**真的移动**，不要站在原地转 |
| **保持朝向大致向前** | 不要边转圈边拍；平移为主、转动为辅 |
| 相邻帧位移 | 不超过画面宽度的 30%（走慢一点） |
| 画面内容 | 要有墙角/门框/家具/地面纹理；避免长时间只拍白墙 |
| 时长与帧率 | 30~60 秒，1080p 60fps，抽 2~4 fps 即可 |
| 光线 | 稳定、别逆光；关掉会闪的灯 |

**只要有了真实平移，深度的病态性就消失了，画质会有质的提升。**

**2. 首次重建先跑 exhaustive**

```bat
call tools\msvc-env.bat
python pipeline\colmap_recon.py --images <帧目录> --workspace <工作区> --matcher exhaustive --use-gpu 1
```

看注册率是否 ≥60%。是的话再训练；不是的话先补拍。

**3. 训练命令（本次验证过的最佳配置）**

```bat
python pipeline\train_gsplat.py --data <COLMAP工作区> --images <帧目录> --out <输出> ^
    --iterations 30000 --downscale 2 --sh-degree 3 ^
    --lr-scale-factor 0.4 --prune-scale 0.05 --eval-views 6

python pipeline\to_splat.py --ply <输出>\point_cloud.ply --out data\models\<名称>.splat --max-scale 0.5
```

**4. 可继续调优的方向**

- `--downscale 1`：8 GB 显存下若 450×800 能跑，可以试全分辨率（本次 30k 步约 11 分钟）
- `--iterations 60000`：SSIM 还在缓慢上升
- 相机模型换 `SIMPLE_RADIAL`：若确认手机畸变校正良好，少两个参数更稳

  `<out>-rejected/`（COLMAP 的 `--image_path` 会递归扫子目录，所以放在里面等于没过滤）；
